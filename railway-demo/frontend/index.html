Tab 2 · The Problem

One berth, two simultaneous checkouts.

A railway seat is shared state. The vulnerable operation is a check-then-act sequence: read status, decide that the berth is available, then insert a booking and update the seat. Without synchronization, the operating-system scheduler can switch threads during database or payment I/O.

At the same millisecond

Process-1 and Process-2 both execute SELECT status and see AVAILABLE. Both pass the check, then both write a booking. The last seat update hides the lost update, while the two booking rows expose the double-booking conflict.

Why it is nondeterministic

Thread scheduling and I/O timing decide which interleaving occurs. The lab adds a controlled delay and barrier so the unsafe interleaving can be observed reliably instead of depending on luck.

Process-1: read AVAILABLE ─────┐
                                ├─ both confirm ── two bookings, one berth
Process-2: read AVAILABLE ─────┘

How the race unfolds

Mutual exclusion

Only one thread may change a particular seat at a time.

Atomicity

Availability check and ticket commit must act as one indivisible operation.

Progress

A free berth should remain bookable; one waiting thread must not block unrelated seats.

Bounded waiting

High demand needs a finite queue and workers that eventually serve waiting requests.

Project objectives

  • Demonstrate a check-then-act race using concurrent passenger threads.
  • Compare unsafe and synchronized outcomes against the same SQLite seat state.
  • Use per-seat locks to allow independent seat bookings in parallel.
  • Model high traffic with a bounded producer-consumer booking queue.
  • Relate event logs and seat-map conflicts to operating-system concepts.
  • Keep the database local and repeatable for classroom demonstrations.
Tab 3 · The Solution

Make the critical section exclusive.

A mutex protects the complete read → check → write sequence. In this application each seat has its own threading.Lock, so requests for unrelated berths can proceed in parallel. The semaphore mode adds a producer-consumer queue with a fixed capacity of five.

Mutex: one owner at a time

wait(mutex) acquires exclusive access; the seat check and booking commit happen inside the critical section; signal(mutex) releases it even when the booking is rejected.

Semaphore: coordinate queue slots

empty counts free buffer slots and full counts queued requests. Producers wait for empty; consumers wait for full; both acquire the buffer mutex only after their semaphore wait succeeds.

wait(seat.mutex)
try:
    if seat.status == AVAILABLE:
        commit_booking(seat, passenger)
    else:
        reject_booking(passenger)
finally:
    signal(seat.mutex)

Synchronization flow

Request seat lockRead + check statusCommit or rejectRelease lock

Why per-seat, not global?

A mutex per berth serializes only competing requests for that berth. Two passengers booking different seats can enter their separate critical sections at the same time, improving throughput without weakening correctness for either seat.

SQLite and the process boundary

A Python lock coordinates threads sharing this application process; it does not coordinate separate server processes. In a multi-worker deployment, use an atomic conditional update or a short BEGIN IMMEDIATE transaction, and enforce booking invariants in the database. SQLite serializes writers, but a stale read made before a write still needs protection.

Lock ordering: wait on empty or full before acquiring the queue mutex. Waiting while holding the mutex can prevent a consumer or producer from making the change that would satisfy that wait.

How it works · Operating Systems concepts & live code inspector

Critical section & race condition

Check-then-act is not atomic. A context switch during I/O lets two threads both read AVAILABLE before either records the ticket. SQLite serializes writes, but cannot repair a stale decision made before the write.

Fine-grained mutex

Each berth gets its own threading.Lock. The read → availability check → write stays exclusive for that berth, while bookings for different seats can proceed concurrently.

Semaphore & bounded buffer

empty starts at 5; full starts at 0. Producers wait for empty and consumers wait for full before acquiring the buffer mutex. This bounds queue memory and avoids holding the mutex while waiting.

Viva quick questions · concurrency and SQLite
Why use a per-seat lock instead of one global lock?

A per-seat lock serializes only requests competing for the same berth. Different seats can be booked concurrently, avoiding a global bottleneck while preserving mutual exclusion for each seat.

Why wait on a semaphore before acquiring the buffer mutex?

A producer first waits for an empty slot, or a consumer waits for a full slot. If either waits while holding the mutex, the other side cannot enter the buffer to create the slot or item needed to wake it, causing deadlock.

Why does SQLite still need application-level synchronization or a transaction?

SQLite serializes database writes, but that alone does not make an earlier availability read atomic with a later write. A process-local Python lock coordinates threads in one server process; multi-process deployments also need a short transaction such as BEGIN IMMEDIATE, an atomic conditional update, and database constraints.

What happens if the simulated I/O delay is removed?

The vulnerable window becomes smaller, so the race may occur less often and become harder to reproduce. It does not become correct: timing is still nondeterministic. The demo uses a controlled delay and barrier to make the unsafe interleaving observable.
